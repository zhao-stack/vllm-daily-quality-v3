# 统一 CI 闭环

入口：已按 SKILL.md 确定升级类型和责任区间，用户任务包括实施/推进该升级 PR。始终保留该类型的修改限制，尤其 tag-only 的人工确认边界和接续 PR 的旧区间归属。

执行前读取当前仓库的 workflow、复用 workflow、测试执行脚本及评论命令实现，确认标签、前置依赖、双版本来源、测试选择、并发取消机制和实际评论语法。不能用历史配置或注释替代当前执行代码。

## 阶段 1：首次全量诊断

1. 首次运行前，以独立 Signed-off-by commit 临时调整真正控制测试停止的 workflow/脚本，使一个测试文件失败后同分片后续文件继续，其他独立分片继续。
2. 保留每个失败的原始日志/结果，并最终汇总非零退出或失败状态；不能仅靠 YAML continue-on-error 将失败标为成功。区分同文件用例、同分片文件、不同矩阵任务及依赖任务的执行行为。
3. 添加 main2main 标签触发双版本全量 CI，确认标签产生了实际事件及运行。如果标签已存在，检查现有运行；需要新事件时按当前实现移除再添加，避免重复触发。
4. 等本轮相关运行结束再撤销诊断或推送下一轮，避免 cancel-in-progress 中断收集。持续记录最新状态，不把运行中当成已完成。
5. 保存 PR head SHA、两个上游实际版本/来源、run/job 链接、失败用例、首个有效错误、日志，以及未执行/跳过/取消/超时/环境阻塞的项目。

“全量诊断”表示尽可能暴露完整问题，不承诺一次全部执行。CPU UT、构建或安装等前置失败可能阻止 NPU/E2E 启动；记录阻塞和未执行覆盖，不能擅自绕过前置门槛。修复前置问题后继续补齐覆盖。

## 阶段 2：记录、撤销诊断、按根因修复

1. 本轮结束并保存证据后，移除 main2main 标签。
2. 精确撤销本轮临时继续执行修改，以独立 Signed-off-by commit 恢复正常策略；不回滚其他人的 workflow 改动。
3. 按下表分类每个失败，再依据当前升级类型及区间决定归属和修改权限。
4. 修复前定位上游 PR 的具体变动及下游因果链；每个独立适配点单独签署提交，推送并同步 PR 描述。

移除标签不会自动取消已运行任务；推送仍可能触发其他 CI。依据当前事件与并发配置检查实际运行，不假设“去标签后不再触发”。

| 失败分类 | 行动 |
|---|---|
| 本次负责区间引入 | 证明原因后，按本类型允许的范围修复 |
| 仅怀疑环境问题 | 收集证据，尚未证实前保留 unresolved，不改业务逻辑 |
| 已确认环境问题 | 等其他问题处理、其余 CI 跑完及环境恢复后，通过适用评论命令重跑 |
| pre-commit 环境问题 | 环境恢复后 /rerun；核对实际 SHA 和运行 |
| pre-commit 由 PR 修改引入 | 修复本 PR 的格式或检查问题 |
| 下游新增测试未适配上游变化 | rebase 后重新定位，按根因决定修测试还是实现；保留原有断言标准，遵守区间归属及 tag-only 确认规则 |
| 前序 PR 的旧区间引入 | 由旧 PR 修复，再同步新 PR，更新基线/扫描有效性及验证 |
| 无关历史缺陷 | 记录，不夹带修复 |
| 持续外部阻塞、权限或网络问题 | 报告阻塞、未完成覆盖和恢复条件；没有新证据/状态变化时不机械重复相同操作 |

## 阶段 3：评论定向验证

1. 查当前评论命令实现，使用支持的方式触发失败测试；支持批量时可一次指定多个文件。
2. 检查机器人产生的实际 run/job，确认修复后的 head SHA、上游版本和目标测试均正确，且测试实际执行。评论被接受不等于执行成功。
3. 若方案不能解决问题，撤销已证实无效的修复，重新定位后修复验证。暂未执行或被环境阻塞不能据此判定方案有效或无效。
4. 定向验证覆盖受影响的版本线路；最终仍执行双版本全量验证。

| 评论命令 | 使用边界（执行时以当前实现为准） |
|---|---|
| /e2e path1 path2 ... | 仅支持实现允许的 E2E 路径；不假设支持 UT、任意路径或 pytest nodeid |
| /rerun | 适用失败任务的重跑；新 push 后必须核对是否有当前 head 的可重跑任务，旧 SHA 的绿灯不能验证新修复 |
| /run | 按当前实现和标签选择触发；确认实际范围及两个上游版本，不能假设总是全量 |

## 阶段 4：重新全量验证与跟进

1. 本次升级引入的问题已修复、定向验证通过，且临时诊断已撤销后，重新添加 main2main 标签。
2. 确认最新 head 在正常策略下启动双版本全量 CI，检查选择范围、前置依赖、跳过项和真实执行结果。
3. 持续监控至完成；新出现的升级问题回到根因分析和定向验证，环境问题按分类处理，旧区间问题同步前序 PR。首次诊断修改默认不重新引入。
4. 在最终 head 的双版本必要任务全部通过且预期覆盖执行完成前，不宣称升级成功。若 rebase/同步/推送改变 head，重新判断证据有效性，不能沿用旧 head 全绿作为最终结果。

任务可持续推进时继续跟进；遇到需要人工确认的具体修改或无法推进的外部阻塞，保留当前 SHA、运行链接、失败分类、已做修复和下一恢复条件。不要自动合并 PR，也不要把阻塞说成完成。
